# NextGen ERP Desktop — Development build

This is an incremental Windows source build based on the supplied v7 archive. It uses Python, PySide6, and a local SQLite database.

## Install and start

1. Extract the project folder to a location you can write to.
2. Install Python 3.10 or newer and enable the Python launcher or add Python to PATH.
3. Run run_windows.bat. The launcher checks for PySide6 and will attempt to install it if missing.
4. On a fresh database, choose the business name, starter profile, currency, theme, and administrator credentials in first-run setup.
5. Sign in using the account you created. The profile enables its configured starter modules; advanced industry workflows still vary by profile.

The database is stored in %APPDATA%\NextGenERP\nextgen_erp.db.

## Existing v6 data

The app uses the existing database in place and does not delete it. If it detects the original admin / ChangeMe123! credential, it asks the owner to replace that credential before sign-in. Keep a separate copy of the database before upgrading or changing computers.

## Current capabilities

- New installations have no shared default password. Passwords use salted PBKDF2-HMAC-SHA256 hashes. Fresh installations start in the warm vanilla light theme; existing saved theme preferences are preserved. Theme changes rebuild styles from shared semantic palette tokens and restore unsaved form values and table selections.
- Admin, Manager, Staff, and administrator-created custom roles have different application access. Administrators can create custom roles from least-privilege Staff or Manager templates, then assign enabled module visibility, action grants, and dashboard widgets; Staff initially receive Sales, Inventory, and CRM. These module grants persist locally and are enforced in navigation, generic records, and core operations. Privileged actions (system configuration, user management, backup, sync, deletion) remain Admin-only. Role checks are enforced in UI actions, the SQLite Store, and the core operations service. This is application-level access control; a local machine administrator can still access the database file directly.
- Built-in profiles can enable a starter module layout and add profile-specific workspaces such as Repair Tickets, Menu & Recipes, Appointments, Batches & Expiry, or Students & Enrolment. Existing records and custom module definitions are preserved. The dashboard has role-specific selectable metrics, a seven-day completed-sales chart, finance summary, quick actions, and recent activity; selected widgets are filtered by enabled module access and action grants. Module dependencies are enforced in the Store: Sales and Purchases require Inventory and Finance, and profile-specific modules require their configured supporting modules. Menu & Recipes, Appointments, Batches & Expiry, and Students & Enrolment remain configurable record workspaces. Repair Tickets now has a dedicated service workflow for intake, diagnosis, customer estimate approval, stock-backed parts, ready-for-collection billing, payment, collection, event history, and printable job sheets.
- Product inventory includes SKU, barcode, category, unit, cost and selling price, reorder threshold, and a stock movement ledger. Non-empty barcodes are unique, sales line selectors accept a scanner-entered barcode or SKU, and the inventory table shows category and barcode. Sales check available stock and reduce it; purchase receipts add stock and update weighted average product cost. Related transaction, stock, cash, and sync queue changes use one SQLite transaction.
- Sales support saved quotations that can be sent, accepted, and converted once into stock-backed sales with payment records. Purchase orders and receipts support multiple product lines, partial payment records, history, and controlled cancellation. Purchase orders can be partially received and remain linked to the generated receipt. Receipts can be cancelled with matching order quantity corrections; cost reversals are rejected if later stock activity would make valuation unsafe. Item-level sales returns validate remaining sold quantity, record whether goods are restocked, write a refund and audit identity, and preserve return history. Returns refund original item value plus the stored proportional sales tax and are limited to the paid balance; customer credit is not supported. Cancellation preserves the transaction and reverses only unreturned sale quantities; purchase cancellation is blocked when it would create negative stock.
- Finance currently provides a cash ledger for receipts, payments, refunds, and manual cash movements. It is not double-entry accounting, tax accounting, or an accounts receivable/payable ledger.
- Legacy generic records remain in the database and are accessible from each upgraded module's legacy-record view.
- Database backups use SQLite's online backup API and let the user choose the destination. Restore validates the backup, migrates a temporary copy, creates a pre-restore safety backup, and then replaces the live database.

## Known limitations

Customer credit and unpaid-balance returns, advanced quote revisions, terms and attachments, supplier delivery documents, purchase/input tax, tax-inclusive pricing, per-product tax categories, double-entry accounting, and complete industry-specific operations remain incomplete. Repair Tickets is a focused workflow for device service businesses; the other profile-specific workspaces are still configurable records. Sales and quotations can use one administrator-configured added-on tax rate; verify the applicable rules yourself because it is not a fiscal or jurisdiction-specific implementation. A full sale cancellation assumes all sold items are returned to stock. Cloud sync requires a compatible trusted server and has not been validated against one. Transaction HTML templates now cover sales invoices/receipts, quotations, purchase orders, goods-received notes, and repair job sheets, with 58/80 mm, A6, A5, A4, A3, Letter, and Legal choices. These documents are not fiscal receipts or tax-compliant invoices, and physical printer output is unverified. Logo management, profile-specific automatic dashboard presets, per-user exceptions beyond role-based grants are not implemented.

## Verification

Run the automated checks from this folder with this command:

    python -m unittest discover -s tests -v

The current 60-test suite covers first-run setup validation, business name/profile/currency/theme persistence, profile starter-module application, administrator creation, and custom field definition and record validation at the Store boundary, valid/invalid/inactive sign-in, sign-out and successful re-entry, legacy default rotation, action grants and role module visibility at Store and service boundaries, custom role creation/deletion, protected-grant rejection and account assignment, theme-state preservation, light/dark palette and accent contrast, module-grant persistence, profile preservation and dependency validation, protection against disabling workspaces with saved records and dependency retention when profile layouts change, role-specific dashboard widget persistence and rendering, permission-filtered low-stock counts and actionable product details, configurable tax settings, settings-form save, product category/barcode persistence, barcode uniqueness and sales-line scan selection, existing-product preservation during v8-to-v9 product catalog migration, stock-backed sales, purchase orders and partial receiving, safe cost reversal rules, quotation conversion, printable document generation, item-level returns and cancellation rules, repair intake through collection and module permissions, cash totals, backup restoration and migration, invalid backup rejection, account status/password administration, and offscreen UI construction. The offscreen environment used for automated tests has limited font availability. A separate isolated Windows desktop preview was checked in both themes at 1274×720, but only the dashboard shell was visually inspected. First-run setup and authentication are method-tested with isolated data; setup/login dialogs were not visually reviewed, and full process restart is not end-to-end tested. All dialogs and modules, target laptop sizes, physical printers, cloud sync, and tax/fiscal output have not been tested. Restore and migration have only been tested with synthetic databases, not real customer databases. See TEST_REPORT.md for the environment and exact limits.
